BusBuddy Phase 1 Architecture and Accessibility Audit
Domain Isolation, Fare Authority, Service Lifecycle, and Phase 2 Requirements
Independent technical review
19 September 2026

Executive verdict
Phase 1 is directionally strong. Pure-Dart entities, typed failures, one authoritative fare engine, and a
shared composition root remove several common sources of divergence. A green 214-test suite is also a
credible regression baseline. The architecture is ready to enter Phase 2 only after three contracts are
made explicit:
1. P0 Fare precedence and rounding: specify whether the VIT Main Gate–Katpadi Railway Station
fare is always Rs. 20 before concession or whether hop tiers can override it. Represent money in
integer paise and define the rounding point and method.
2. P0 Singleton ownership and asynchronous teardown: give every timer, stream subscription,
controller, and lifecycle listener one owner; make start/stop idempotent; and make test reset await
complete disposal before installing replacements.
3. P0 Do not cap platform text scaling: the research document says scaling is clamped to 0.85–
2.0. That can reduce or block a user’s accessibility setting. Phase 2 should preserve the platform
TextScaler and make layouts reflow at large text and display sizes instead.
No Dart source tree was included in the review workspace. Consequently, the items below are risks and
acceptance criteria derived from the Phase 1 description and the supplied project documents, not claims
that a particular implementation line is defective. A short source inspection should be used to close each
item.

Evidence and consistency observations

The audit used the supplied implementation research document, updated project handoff, and README.
They consistently require deterministic transport facts, a map-independent journey path, meaningful
TalkBack output, multimodal feedback, and user control over personalization. Those are the correct
architectural anchors.
Two document-level discrepancies should be corrected so that the repository has one trustworthy baseline:
• The README reports 111 passing tests, while the Phase 1 completion statement reports 214. Generate
the badge/count from CI rather than maintaining it manually.
• The handoff still describes production implementation and ticketing as pending or future, while Phase
1 reports both as implemented. Mark the handoff as historical or add a dated architecture decision
record (ADR) that supersedes it.

2.2

Fare engine and rounding

The current numbers happen to avoid fractional rupees: a 40% concession means paying 60%, producing
Rs. 9, Rs. 12, and Rs. 15 for the three stated tiers. That does not remove the need for a money policy;
future fees, taxes, or percentage changes will expose binary floating-point and rounding differences.
Recommended authoritative sequence
1. Validate passenger type, route, direction, and ordered stop occurrences.

2.3

Service locator lifecycle and races

Replacing approximately 19 local repository/data-source constructions with shared instances removes
duplicate simulation loops, but it also concentrates lifecycle risk. Enforce the following ownership model:
• Composition root owns disposal. Widgets may subscribe and unsubscribe, but must never dispose
locator-owned repositories or app-scoped controllers.
• Single-flight initialization. Concurrent getters must await the same initialization future; they must
not create two instances during startup, resume, or test override.

• Idempotent operation. Repeated start(), stop(), dispose(), pause, and resume calls must be
harmless and covered by tests.
• Await cancellation. Stream subscription cancellation may complete asynchronously. Make the reset
hook return Future<void> and await subscriptions, databases, sockets, and controllers before clearing
references or installing overrides.
• Invalidate late work. Tag callbacks with a generation/session ID or cancellation token so an old
timer, route request, payment callback, or bus stream cannot update newly installed state.
• Lifecycle policy. Define which simulation, GPS, audio, socket, and announcement activities pause in
background/inactive states and how a fresh snapshot is obtained on resume.
• No hidden re-creation. After reset/disposal, a stale widget reference must fail safely; a lazy getter
should not silently recreate half of the graph while old controllers still exist.
• Scoped state. Keep infrastructure app-scoped, but make journey/session state explicitly replaceable.
Prefer constructor injection into screens/controllers over calls to a global locator deep in the widget
tree.
Add stress tests for: two simultaneous first reads; rapid start/stop; background/resume; route pop during
an in-flight result; override/reset while a timer tick is queued; and repeated test setup/teardown. Run
these tests with fake time so failures are deterministic.

2.4

Accessibility-specific race conditions

Shared state can create duplicate or contextless output even when the data is correct. A hidden screen
may still listen to a bus stream and announce ETA changes; an old async result may move focus after
navigation; and the global assistant overlay may obscure the current control or become interleaved
unpredictably in traversal order.
Create one application-level announcement coordinator. It should accept semantic events rather than
raw data ticks, deduplicate them, prioritize safety/actionable events, suppress output from inactive routes,
respect speech/haptic preferences, and never compete with assistant audio. Normal rapidly changing
data belongs in a visible text status region; spoken announcements should occur only on meaningful state
transitions. Flutter notes that live-region announcements are polite and can be dropped while another
accessibility announcement is in progress, so safety-critical alerts also need persistent visual/text state
and, where appropriate, haptic or notification fallback.
The floating assistant needs an explicit interaction policy:
• collapsed bubble: one labeled button in a predictable traversal location, never covering the focused
control;
• movement: provide non-drag actions such as move left/right/top/bottom or reset position;
• expanded non-modal panel: define how users move between panel and page without focus loss;
• modal mode, if used: trap focus, announce the panel title, restore focus to the invoker on close, and
remove obscured content from accessibility traversal;
• full-screen assistant: stop or hide the overlay semantically as well as visually.

Question 2: highest-leverage Phase 2 requirements

P0 architecture gates
1. Publish contracts before widgets. Add ADRs for fare precedence/rounding, lifecycle ownership,
journey state transitions, stale-data handling, announcement policy, and overlay behavior.
2. Use semantic design tokens. Define tokens by purpose—for example color.action.primary,
color.status.warning, space.controlGap, size.touchTargetMin, text.body, motion.reduced—
rather than feature-specific hex values. Every status token needs light, dark, and high-contrast values
plus a non-color cue.
3. Preserve platform accessibility settings. Do not reduce the system text scale and do not impose
a 2.0 ceiling. Use the platform TextScaler, responsive constraints, wrapping, scrolling, and content
reflow. Treat overflow at large text/display size as a failed test, not a reason to clamp.
4. Make semantics part of component APIs. Reusable controls must require an accessible name,
role/action, state/value, disabled reason where relevant, and optional hint. Decorative nodes must be
excluded; compound cards should avoid duplicate child speech.
5. Centralize side effects. Navigation, focus changes, speech, haptics, snackbars, and notifications
must be emitted from explicit effects/state transitions, not opportunistically from repeated widget
builds.
6. Adopt explicit asynchronous view states. Every data surface supports loading, content, empty,
stale, offline, permission-denied, recoverable error, and terminal error. Each state exposes the next
action in plain language.

P1 accessibility gates
7. Task-first focus order. The next journey action comes first; decorative maps and animations do not
precede it. On navigation, place focus on a meaningful page heading and restore focus after dialogs.
Current Flutter semantics should use headingLevel for document structure rather than relying only
on the older boolean header flag.
8. Map equivalence. Every bus position, route, stop, ETA, direction, selection, and stale/error
condition available on the map must also be operable and understandable through a list/card/text
path.
9. 48-by-48 is a floor, not the whole policy. Also enforce spacing, no gesture-only actions, clear
disabled states, and alternatives for drag, swipe, long press, and precise map interaction.
10. Reduced motion and interruption control. Disable non-essential pulsing, route animation, and
auto-scrolling when reduced motion is requested. Never auto-move focus or open a surface because a
timer/data update fired.
11. Plain-language recovery. Map each structured Failure to a stable user message, recovery action,
and accessible announcement priority. Do not expose exception strings or silently swallow failure
cases.
12. Privacy and safety boundaries. Emergency sharing, microphone, location, camera, ticket purchase,
and concession proof require explicit purpose, permission timing, confirmation, cancellation, and a
non-voice alternative. AI must not initiate payment or present probabilistic recognition as guaranteed
identification.

Definition of done for every Phase 2 screen
A screen is complete only when it:
• works without color, animation, map imagery, speech, or network as its sole information channel;
• has a deterministic initial focus and logical traversal order;
• remains usable with platform text/display scaling and both portrait and landscape constraints;
• exposes loading, empty, stale, offline, permission, and error recovery states;
• contains no gesture-only operation and meets minimum target size/spacing;
• emits no duplicate, rapid, hidden-route, or contextless announcements;
• passes automated semantics checks and a recorded manual TalkBack checklist.

2. Build the token package and an accessibility-aware component catalog in an isolated gallery, covering
buttons, fields, cards, status banners, dialogs, bottom sheets, lists, and map alternatives.
3. Implement the announcement/effect coordinator and route/focus policy before live screens consume
shared streams.
4. Rebuild one complete vertical slice—search → route result → active journey—and validate it with
TalkBack and maximum text/display settings.
5. Only after the slice passes, migrate ticketing, safety, customization, and the assistant overlay. This
prevents inaccessible patterns from being multiplied across the application.

Conclusion
The greatest Phase 2 risk is not visual inconsistency; it is allowing global live state, announcements,
overlays, and text-scale overrides to become implicit UI behavior. Keep domain and fare decisions
deterministic, make singleton ownership observable and awaitable, and treat semantics/reflow/focus
as component contracts. With those gates, the Phase 1 refactor provides a solid foundation for an
accessibility-first rebuild.
